That means architecture, debugging, testing, state management, and the unglamorous business of shipping one product across Android, iOS and web. Backend and platform work: Go, databases, cloud services, server-side functions. The thread through all of it is that I've worked at several levels of the stack and have usually had to learn the unfamiliar parts quickly. Being able to walk into a system I don't know, find the problem and become useful in it is probably the most portable thing I've learned.

Which project or piece of software are you most proud of, and why?

DawaMom, a maternal-health initiative I co-founded at university. It began with a problem rather than a technology. We were looking at how frontline healthcare workers could use better data to spot risk earlier and make decisions with more information, in places where specialists are scarce. There was no version of that where the software got to be clever and the clinical workflow could be ignored. So the project pulled in software engineering, data, healthcare workflows, mobile, screening and imaging concepts, and a great deal of operational reality. A system the people running it can't depend on, understand or fit into their existing process is worthless, however good the architecture is. I learned that the hard way, on that project. It also changed how I work: start with the problem, understand the users and the constraints, then decide what to build. The same order applies at MediTracker and in my FlutterFlow work. The pride is in that more than in what we shipped.

Outline your thoughts on quality in software development. What practices are most effective to drive improvements in quality?

Quality belongs to the whole team, and it isn't a phase. A good system is correct, reliable, secure, observable, maintainable, and understandable by the people who inherit it. The mechanism that matters most is feedback. Clear requirements and interfaces up front, then small reviewable changes, automated tests, code review, static analysis, CI — anything that catches a mistake earlier than the customer does. Defects get more expensive the longer they survive. On testing, I care about the right level more than the volume. Unit tests for local behaviour and edge cases; integration and end-to-end tests where components meet. Chasing coverage as a number is a mistake. A small suite the team trusts beats 95% that nobody reads. Observability is the other half, and it's usually what gets skipped. Logs, metrics, traces, error reporting, health checks. If I can't see how the thing behaves outside my own machine, I'm guessing. Then simplicity, which I think is badly underrated as a quality practice. Every dependency, abstraction, configuration option and moving part is another failure mode. Removing complexity is often the actual fix. And when something does fail in production, the review should find the conditions that allowed it and change something real. Blame isn't a corrective action.

Outline your thoughts on documentation in software projects. What practices should teams follow?

Documentation is part of the software, not something written afterwards. Its job is to reduce the amount of knowledge that exists only in somebody's head. First principle: put it where it's needed, as close as possible to the thing it describes. The repository should tell you how to build, test, run and contribute. Design decisions belong next to the code, in version control, so they move when the code moves. Beyond that, I'd organise it around what people are trying to do: - Getting started: how do I install it and get something working? - Concepts: how does the system work and why is it built this way? - Tasks: how do I do a particular operation? - Reference: what are the APIs, configuration, commands and interfaces? - Operations: how do I deploy, monitor, troubleshoot and recover it? - Contributing: how do I change the project and get the change in? Working examples beat abstract description, and where I can, I want those examples tested automatically so they can't quietly rot. API references should be generated from the source or the schema rather than maintained by hand in two places. Comments should explain intent, especially the reasoning behind a decision that looks odd until you know the history. If the code already says it, the comment is noise. For architecture, a short record of the context, decision, alternatives and consequences is enough. Nobody needs a document; they need the reasoning. Documentation needs owners and review the way code does, and that part gets forgotten. Stale documentation is worse than missing documentation, because it is confidently wrong. Review it with the code it describes, and delete what is no longer true. The test I apply: could somebody pick this up without finding me?

What are great examples of open source docs?

The good ones feel like part of the product, not a manual bolted on afterwards. The Linux kernel documentation is the systems-level example: architecture, development process, subsystems, APIs, contribution workflows. It serves beginners and people working inside it, which is a hard balance to hold. Kubernetes is well built for a different reason. Concept, task, reference, example, separated cleanly, so you can learn the idea, do the thing, then look up the detail without wading through everything else first. Go's documentation I like for its restraint. Clear, short examples kept close to the language, the standard library and the tooling. It reads the way the language thinks. Godot is interesting because its audience ranges from complete beginners to experienced developers, and the docs handle both: concepts, step-by-step tutorials, class and API references, worked examples. Volume isn't the common thread. It's clear structure, searchability, examples that run, concepts explained before the reference dump, and maintenance as part of development. That's the standard I aim at, and mostly miss.
