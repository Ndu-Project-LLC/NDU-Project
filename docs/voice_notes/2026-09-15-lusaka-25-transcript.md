## Distilled asks

### 1. The import template is system-generated — and needs a Definitions tab

> "This XO document, did the system auto-generate it, or … how does that export
> template come across?"

Answer given on the call: it is generated by code (a script builds the template
from the table), not uploaded by hand. The owner's conclusion:

> "these tables have number, right? Number one, two, three, four. So, the
> template should have the number too, and this is going to help people … so
> they're able to put it into the template directly"
>
> "So, why do you say add definitions? Here, on this table?" — **"No, in the
> same Excel. So that when they import the Excel, it does not give them
> error … it will just get what's in the specific tab and not get the one that
> has got definitions."**
>
> "So, you're saying you add the second tab for definitions?" — **"Yes."**

Plus the delivery promise: "It'll be ready this week."

So: one workbook, tab 1 = the numbered table rows, tab 2 = what each column
means; the importer reads tab 1 only, so the definitions text can never be
mistaken for data.

### 2. The import must not destroy what is already on the page

> "the functionality still remains of, like, the template … I want you to see
> it"

Raised alongside the Lusaka 24 requirement that an import adds to the bottom
rather than replacing.

### 3. Project Milestones must not contain opportunities or allowances

> "why is the opportunity still showing up here under the allowance, under the
> project milestones, because they are not milestones?"
>
> "I hope you are taking notes, so that those can be erased, so you can address
> all of these key errors of your finding"

This was explicitly flagged as a low-hanging fruit to fix immediately
("my suggestion will be today, tomorrow morning"), not a "this week" item.

### 4. Procurement items should not appear in the initiation phase

> "For the most part, in initiation, we are not actively doing all the
> [procurement] … That should not be seen in initiation."
>
> "But it's not a highest priority right now … it's something that I do want to
> note again, because … we don't get lost in that in the initiation phase."

Nuance raised in the same breath: long-lead items *do* need to be identified
early, so the fix is about **when procurement execution is shown**, not about
hiding the need to order early.

### 5. AI stays off; the code-level paths are what must work

> "So it's not AI because AI is off, right? … that's why I like this AI being
> off, to be honest, because we have to understand how this thing functions at
> the code level"
>
> "So, how am I going to remove this from here? … you're going to go into the
> code and get this out and not have it tied in here again?"

Also on the process, for the record: "this week" is not an answer —
low-hanging fruit gets done today/tomorrow morning.

## Still open from this note

1. **Ask 4 — procurement shown in initiation.** Needs the initiation-phase
   procurement surface identified and scoped to identification only; the owner
   explicitly deprioritised it behind ask 3.
2. **Ask 2 — "download template and re-import" pop-up.** The template download
   and the import dialog both exist; the guided pop-up that offers the template
   download before an upload does not.
3. Decide what `Apply To: Schedule` on an opportunity/allowance should feed now
   that it no longer writes milestones (see the note below) — otherwise the tag
   is silently inert.

### Note on the now-inert `Apply To: Schedule` tag

Opportunities and Allowances still offer `Schedule` as an Apply-To destination
(in `front_end_planning_opportunities_screen.dart` and
`front_end_planning_allowance.dart`). Since ask 3 removed the milestone write,
tagging `Schedule` no longer changes anything downstream. Removing the option
would invalidate persisted tags, so it was left in place and flagged here:
either the tag needs a new destination (e.g. schedule risk/opportunity
annotations) or it should be retired with a migration.
