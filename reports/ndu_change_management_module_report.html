4. How the Change Control Process Works

4.1 Change request lifecycle

Each change request moves through ten explicit statuses (change_management_models.dart:90):

Draft Submitted Under Review Pending Approval Approved Rejected Returned for Revision Implemented Closed Emergency

4.2 Change types

Fifteen change categories are supported (change_management_models.dart:12): Scope, Schedule, Cost, Resource, Procurement, Contract, Risk, Quality, Regulatory, Product, Requirements, Technical, Defect, Compliance, and Operational — each with its own icon and color treatment.

4.3 Impact assessment — 15 dimensions

Every change is assessed across 15 dimensions (change_management_models.dart:206): Scope, Schedule, Cost, Resources, Procurement, Contracts, Risks, Quality, Safety, Stakeholders, Funding, Benefits, Dependencies, Interfaces, and Technical. Each dimension carries an impact level (0–5 slider), optional schedule days and cost amount, a critical flag, narrative, owner, and due date.

  • Composite impact score — weighted average across all 15 dimensions; Scope, Schedule, and Cost carry double weight (2.0) as primary constraints; result is in [0, 5].
  • Total cost impact and total schedule impact — summed across approved/implemented changes for dashboard visibility.
  • Re-baseline trigger — any change with cost or schedule impact > 0 flags requiresRebaseline, feeding the re-baseline detection on the dashboard.

4.4 Approval workflow

Approvals run through a step-by-step workflow builder (change_management_models.dart:384). Ten approval roles are available: Project Manager, Project Controls, Engineering Lead, Quality Manager, Procurement Lead, Finance, Sponsor, Safety Officer, Regulatory Authority, and Change Board. Each step records one of seven decisions: pending, approved, rejected, request info, return for revision, delegated, or escalated. The workflow can be finalized once all steps are decided, and the decision history is preserved.

4.5 Emergency changes and Agile mode

  • Emergency changes are flagged at creation, automatically get Emergency priority, and enter the Emergency status lane so they can be fast-tracked through the workflow.
  • Dual delivery-model support — Waterfall projects follow a strict management-of-change process; Agile projects can register routine refinements separately from controlled baseline changes.

4.6 Implementation and baseline control

  • Apply to baseline creates a baseline revision, updates the current BAC, scope hash, and baseline finish date, and draws down contingency ($500K default) and management reserve ($1M default).
  • Rollback reverts the baseline to the previous revision and restores contingency/reserve.
  • Baseline history is recorded per revision with revision date, and the dashboard tracks re-baseline count per quarter plus average approval cycle time.
Why this is a complete loop: request → assess (15 dimensions) → approve (multi-step workflow) → audit (trail + CSV) → implement (apply/rollback) → re-baseline (revision history). No stage depends on a future feature; all of it is usable today.

5. Data Model & Security

Persistence

  • Change requests, audit trail, and baseline history live under the user's Firestore domain (users/{uid}/changeManagement/) with real-time listeners.
  • Provider loads on init and falls back to an empty state — it never invents phantom or demo change requests (change_management_provider.dart:1).
  • CR numbers are generated sequentially per year (CR-2026-001 style), and every create/update is written through to Firestore.

Security rules

  • User-scoped collections changeRequests, cmAuditTrail, and cmBaselineHistory are read/write restricted to the authenticated owner (firestore.rules:41).
  • The project-level change_requests collection is scoped to the requester plus the project owner and admins (firestore.rules:263) — the previous any-authenticated-user read was removed.

6. AI Integration

  • Auto-population from project context — the module seeds change requests from the project's accumulated constraints and delivery context (buildAccumulatedContext('change_management')), giving the register a grounded starting point instead of blank rows.
  • AI recommendations — the Change Management tab inside Project Controls surfaces AI-generated recommendations derived from project constraints.
  • Secure AI stack — AI features run on the migrated GPT-5.x stack: normalized payloads (max_completion_tokens + reasoning_effort) via the secure openaiProxy Cloud Function, with an optional self-hosted LLM server (Ollama + auth-gate) for provider-outage resilience.

7. Verification & Quality

  • The module ships with its state management isolated in a dedicated provider with getter-computed metrics (open CRs, pending approvals, approval cycle time, quarterly re-baselines, total cost/schedule impact), so dashboard KPIs are derived, not hard-coded.
  • Persistence is wired end-to-end — CR creation, every update, every audit entry, and every baseline revision is written to Firestore at the mutation funnel points (createChangeRequest, _updateCR, _addAudit, applyToBaseline, rollback), and dashboard state (contingency, reserve, BAC) is recomputed from persisted data on reload.
